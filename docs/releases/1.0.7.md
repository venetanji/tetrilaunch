## Review and verification

Review covers the `v1.0.6..staging` delta, release metadata, packaged Linux evidence and release workflow safety. The historical 1.0.6 review is background, not evidence that its old findings still apply.

- `migrations/`, tier funding rules, upgrade budgets, run/meta state and save loading are unchanged from v1.0.6. No database migration, save migration or leaderboard clear is needed. Do not use the README's historical economy-reset instructions for this release.
- The three store workflows already enforce app/desktop/tag version agreement. Android has its own tag trigger; a desktop signing failure no longer silently suppresses Android.
- A push to main triggers no production Worker or store-release workflow. `production.yml` is manual; the three store/desktop release workflows start on a `v*` tag. Steam upload remains a separate dispatch.
- Browser CI cannot certify Electron packaging, iPhone performance, signing secrets, purchases, or store acceptance. Those remain explicit launch gates.
- The integrated headline fix has automated coverage at tall windowed/fullscreen sizes. Complete controller reconnect, update/save-retention, sustained crowded-pile and platform-specific signing tests on the final packaged build.
- PR preview Pages hosting has no isolated account/leaderboard Worker; use the verified staging Worker for server flows. Native test builds need `VITE_API_BASE` configured to staging deliberately; ordinary native builds default to production.

**Packaged Linux evidence:** candidate `15cc0c1`, whose tree is identical to staging `bf53468`, built as a Linux x64 AppImage and ran through native Wayland on a 1920x1080 display at 150% desktop scaling. Menu, Settings, tier hub and live gameplay were visually inspected; Orbitron, Rajdhani, JetBrains Mono and Press Start 2P loaded from the package. Native Ctrl+plus, Ctrl+minus and Ctrl+0 worked in the menu and gameplay. Fullscreen page zoom at 100%, 125%, 150% and 200% kept the tested menu controls visible. No uncaught renderer exception appeared in those tested flows. This test bundle deliberately used the staging API; it is not a production-configured release artifact or macOS/iOS signing evidence.

**Open desktop zoom finding:** on a 1920x1080 CSS viewport, automatic chrome magnification falls from 1.5 to 1.2 to 1 as page zoom rises from 100% to 125% to 150%. This cancels the initial text enlargement; text grows at 200%. Preserving the initial magnification alone creates Workshop/modal fit failures, so no partial fix was applied. Resolve this coherently, or explicitly accept its deferral in the release review, before claiming full desktop text-zoom support. Normal font loading and the current display's 150% scaling passed their checks.

**Steam asset readiness gap:** the existing capture runbook still lists 616×353 main-capsule source frames and half-size header/small/vertical assets. [Valve’s current requirements](https://partner.steamgames.com/doc/store/assets/standard), checked 2026-10-04, are 1232×706 main, 920×430 header, 462×174 small and 748×896 vertical. Reuse the existing capture/assembly tools, but correct the dimensions and verify final artwork before Steam submission; no assets were regenerated in this metadata PR.

**Steam capture/deployment gaps:** `captureScene` in `app/sim/promo/run.ts` currently sets `touch: true` for every store, including Steam. Verify desktop input presentation before final screenshot capture. Reuse the existing 1080p60 H.264/AAC trailer assembly; confirm the current [trailer requirements](https://partner.steamgames.com/doc/store/trailer) instead of treating the trailer as optional. The separate Steam audit identified [the last verified upload](https://github.com/venetanji/tetrilaunch/actions/runs/34861957104/job/104045840700), BuildID `25303655` from `90cd3bc` on 2026-09-14, which predates the controller and hub changes. A green desktop release build does not prove Steam is current: verify actual default/playtest BuildIDs and package/depot assignments in the dashboard before an approved upload.

## iPhone testing before release

The checked-in Xcode project and Capacitor package target iOS 15.0. Confirm the old iPhone model and installed iOS version, then validate the actual signed build's compatibility; a source deployment target alone is not device evidence.

Use [the iOS runbook](../ios.md) and `ios.yml` as the current references; `docs/NATIVE.md` still contains obsolete statements that iOS CI/signing are unavailable.

Current `ios.yml` behavior:

- A branch `workflow_dispatch` is a signing/export rehearsal. It produces a signed IPA artifact and does **not** upload to TestFlight, even if `publish` is selected on a non-tag ref. It is not automatically an installable ad-hoc build.
- Upload requires a `v*` tag: a tag push uploads automatically; dispatch on that tag also requires `publish=true`. A tag also starts Android and desktop release pipelines, so do not create a throwaway release tag merely to test an iPhone.
- A pre-release TestFlight path independent of release tags needs a separately reviewed workflow change and upload approval. Alternatively, use an approved local Xcode device build with the owner's signing/device setup. Neither path is part of this metadata PR.
- `ios-build` requires distribution certificate/password, App Store Connect API key/id/issuer, Apple team id and the RevenueCat iOS SDK key. Google iOS client id is warn-only. Confirm environment approval rules, signing validity, App Store profile/bundle identity, tester access and monotonically increasing build number with the owner. No secret values are needed in this PR.
- On the actual old iPhone: launch/update without losing saves, rotate/background/resume, restart, repeated input, audio interruption, crowded-pile pacing, login, purchase/restore and test leaderboard routing. Record build/commit and device/OS.

## Release procedure

1. Review the fresh `claude/release-1.0.7-review` PR targeting staging. Version metadata already landed through #244; this branch carries the final release record. Review the outstanding device and release findings, then merge this branch into staging last, as #224 did for 1.0.6.
2. Verify the final combined staging commit: both TypeScript configurations, systems/API/trajectory regressions, the UI-fit fleet at zero new/stale/grown entries, web/native builds, store-bundle/copy checks and `RELEASE_TAG=v1.0.7` version agreement. Check current-head CI and the automatically deployed staging build/API.
3. Fast-forward main to that exact verified staging commit and push. A GitHub PR merge into main adds a different commit and does not implement this step. If branch protection refuses the direct fast-forward, report it for an authorized resolution; do not force-push or bypass it through another merge.
4. Deploy the production Worker through its separately approved manual workflow and verify the served commit/API before releasing the production-default native clients. Complete the outstanding device/signing checks and resolve or explicitly accept the zoom finding before the tag is approved.
5. After explicit release approval, create `v1.0.7` only on that main commit and push the tag once. The tag independently starts desktop packaging/GitHub Release, Android Play internal and iOS TestFlight. A branch rehearsal is not a release tag.
6. Steam upload is a separate approved desktop dispatch to `playtest`, with default-branch promotion manual. No database migration or score reset belongs to this release.

From the repository root, step 3 uses:

```bash
git fetch origin
git switch main
git merge --ff-only origin/staging
git push origin main
```

The preliminary main promotion requested after #245 does not replace step 3: merging this release-record PR creates a later staging commit that must also be validated and promoted before tagging.
